# ADR-0014: 导出端点的列契约冻结

- **状态**：已接受
- **记录日期**：2026-11-08
- **相关代码**：scripts/gen_export_contracts.py, tests/export_column_contracts.json, tests/test_export_contracts.py, scripts/seed_ci_fixture.py, agents/persistence/_exports.py, web/backend/main.py, .github/workflows/ci-cd.yml

## 背景

iter #78~#81（ADR-0010 ~ ADR-0013）搭了**四层契约**，每一层都从
「客户到底会碰到什么」出发选判据：

| ADR | 冻结的东西 | 客户碰到的是什么 |
|---|---|---|
| 0010 | Python 公开方法签名 | 客户 import 我们的包 |
| 0011 | HTTP 面（路径/参数/状态码/response_model/鉴权） | 客户调我们的 API |
| 0012 | 响应体运行时形状（字段名 + 类型） | 客户解析我们的 JSON |
| 0013 | 端点自动发现 + 显式豁免登记册 | 客户**不知道**我们有什么端点 |

### ADR-0013 留下的那张欠条

iter #81 把端点清单改成自动发现 + 显式豁免登记册，fail-closed 了。
它把 14 个导出端点（CSV / Parquet / NDJSON）登记成了 `NON_JSON_RESPONSE` 豁免，
豁免 note 里白纸黑字写着：

> 「CSV 全文导出; 字段契约是「列名」, 不是 JSON 字段形状。」

**这句话是对的，但它同时是一张欠条。**

「字段契约是列名」= **列名就是契约** = 列名必须有保护。
而 ADR-0013 交付之后，那 14 个端点的列名**依然零保护** —— 因为前面四层都盖不住它：

- ADR-0010 看的是 **Python 方法签名**，不看返回值内容
- ADR-0011 看的是 **路径/参数/状态码**，不看响应体
- ADR-0012 抽的是 **JSON** —— 而 CSV / Parquet / NDJSON **不是 JSON**
- ADR-0013 是**发现机制**，它只回答「有哪些端点」，不回答「端点返回什么」

于是出现了一个**完整的空洞**：客户下载一个 `.csv` 或 `.parquet` 文件，
拿到手之后**没有任何一层门禁在看它**。

### 客户视角的三种真实事故

1. **列被删了** —— 客户下游 ETL 报「找不到该列」，或者更糟：
   `pd.read_csv()` 之后 `df['total_tons']` 直接 KeyError。
2. **列被改名了** —— 同上，但更难查（客户以为是自己写错了）。
3. **列顺序变了 / 列类型变了** —— 最阴的一类：
   - CSV 客户如果用**位置**读（`awk -F, '{print $5}'`、`df.iloc[:, 3]`），
     中间插一列 → 后面所有列位置右移 → **静默读到别的列** → 报表数字错了但没人报错
   - Parquet 客户如果用 `df['x'].sum()`，类型从 double 变成 string →
     **静默算错**（pandas 把字符串拼起来，而不是报错）

第 3 类正是 ADR-0012 立下的那条原则的延伸：

> 「静默算错比报错更贵」

## 决策

**把导出文件的列契约冻成第五层 CI 常驻不变量，并且额外加一层「同表跨格式一致性」
结构不变量。**

### 判据：每种格式冻它自己的那部分契约

这不是「同一个检查套四种格式」——**四种格式的契约根本不是同一个东西**：

| 格式 | 契约是什么 | 顺序重要吗 | 类型重要吗 |
|---|---|---|---|
| CSV | 列名 + 顺序 | **重要**（位置型读取器） | 否（全是字符串） |
| Parquet | 列名 + 顺序 + **类型** | 重要 | **重要**（schema 自描述） |
| NDJSON | 键集合 | 否（对象无序） | 弱（JSON 有类型但宽松） |
| JSON | 键集合 | 否 | 弱 |

### 方向感：红 / 黄

- **破坏性 → 红**：端点没了 / 列被删 / 列被改名 / **CSV 列顺序变了** /
  **有序格式中间插了一列** / **Parquet 列类型变了** / **同表跨格式列集不一致**
- **兼容 → 黄（只打印，不让 CI 变红）**：新增列（追加在末尾）/ 新增端点

理由和 ADR-0011 一模一样：**门禁一旦「什么变化都报红」，团队就会开始无脑刷基线
—— 那它就废了。**

### 两层检查，缺一不可

**第一层：每端点 vs 基线**（跟 ADR-0012 同一个思路）
真起服务、真调端点，把列契约抽出来写进 `tests/export_column_contracts.json`，
每次 CI 比对。抓的是「**相对上一次**变了什么」。

**第二层：同表跨格式一致性**（推导，**不需要基线**）
同一张表导出成 CSV / Parquet / NDJSON / JSON，**列集合必须完全一样**。
这是**结构不变量**，所以在一份全新的 checkout 上也成立。抓的是「**同一个表在不同
格式下长得不一样**」。

**为什么必须有第二层**：只冻基线是不够的 —— 如果基线本身就是漂移的
（19 列的 CSV vs 20 列的 Parquet 被一起冻进去），门禁会**一直绿，绿得没有意义**。
跨格式一致性检查不需要任何基线，**它永远是真的**。

### 覆盖范围：38 个导出契约面

- **18 个路径导出端点**：从路由表**自动发现**（路径以 `.csv/.parquet/.ndjson/.json`
  结尾的 GET 端点）—— 手写清单就是 ADR-0013 推翻的那个 fail-open 设计，不重蹈
- **20 个 db-export 参数矩阵面**：`/api/admin/db-export?table=X&fmt=Y`，
  5 表 × 4 格式。参数驱动，不能靠路径后缀发现，只能显式枚举**端点自带的封闭列表**

两者都被归到**逻辑表名**下，所以「客户从统一导出入口拿到的表」和「从专用导出入口
拿到的表」会**互相比对** —— 这正是下面三个真 bug 藏身的地方。

## 后果

### ✅ 正面：门禁当场抓出三个真 bug（都不是理论推演，是注入验证过的）

**Bug 1：`export/cycles.csv` 比同表的 JSON/Parquet 少一列 `n_routes`**

- 机制：`export_cycles_csv()` 的 `columns` 列表是**手写**的，漏了 `n_routes`
  （它来自 `get_cycle_history()` 里的一个子查询），而 `csv.DictWriter` 的
  `extrasaction="ignore"` 会把多出来的键**静默丢掉**
- 后果：客户下载 CSV 少一列，下载 JSON/Parquet 有这列 —— **同一个表两个形状**
- 修复：补上 `n_routes`，四个格式的列集合**与顺序**现在完全一致

**Bug 2：`db-export?table=supplies&fmt=parquet` 所有列都是字符串**

- 机制：这个端点原来走「导 CSV 再 parse 回来」拿 rows，
  而 **CSV 往返会把所有值变成字符串**
- 后果：客户拿到 `available_tons` 列类型是 `string` 而不是 `double`，
  `df['available_tons'].sum()` 得到的是 `'10.012.5'` 而不是 `22.5`
  —— **静默算错，而且不报错**
- 修复：改用 `export_*_rows()`（iter #27 就加好了，注释里写着「避免 CSV parsing
  round-trip」，只是这个端点一直没切过去）

**Bug 3：`db-export?table=llm_decisions&fmt=csv` 返回 placeholder 假 CSV**

- 机制：写死了 `"id,note\nllm_decisions,format=csv+not implemented yet\n"`
  —— 它的列是 `id,note`，而 llm_decisions 真正的列有 **14 个**
- 后果：客户下载这个 CSV 拿到的是**假契约**，跟同表其他三种格式完全对不上
- 修复：`_rows_to_csv(rows)` 本来就能直接把 `get_llm_decisions()` 返回的 dict
  列表写成 CSV —— 根本不需要 placeholder

**注入验证**（4 种破坏 → 门禁全部精准报红 → 完整还原 → 回到 OK）：

| 注入的破坏 | 门禁抓到了吗 | 报出来的信息 |
|---|---|---|
| 从 cycles.csv 删掉 `n_routes` | ✅ 红 | 列被删 + 跨格式不一致（少了 `n_routes`） |
| CSV 列顺序变了（`total_tons` ↔ `total_cost_sek`） | ✅ 红 | 位置变化 `total_cost_sek 9→8, total_tons 8→9` |
| db-export 退回 CSV 往返 | ✅ 红 | 列**类型**变了 `number → string`（逐列列出） |
| llm_decisions CSV 退回 placeholder | ✅ 红 | 13 列被删 + 1 列多出 |

### ✅ 正面：判据是「客户会不会炸」，不是「diff 有没有变」

- **位置型读取器**的判据是「**共有列的绝对下标有没有变**」，不是「相对顺序变没变」
  —— 因为中间插一列时，相对顺序不变但绝对位置全变了。
  实测三种情形：末尾追加（兼容）/ 中间插入（破坏）/ 整体重排（破坏）
- **Parquet 列类型**用**类型家族**（string / integer / number / boolean）而不是
  原始 pyarrow 类型串 —— 因为同样的语义在 pandas 2.x 下是 `string`、
  在 pandas 3.x 下是 `large_string`。存原始串会让门禁在「CI 装的 pandas 版本」和
  「本地装的」之间**假红** —— 而假红一次，团队就会开始无脑刷基线，门禁就废了

### ✅ 正面：fixture 必须有明细行，否则冻的是假契约

空表的 Parquet 导出返回的是一个**假 schema**（只有一列 `_empty` int64），
空表的 NDJSON 一行都没有 —— 那种情况下冻下来的契约毫无意义。
所以 `seed_ci_fixture.py` 新增了 `--with-detail`：铺 supply / demand / match /
route / llm_decision 五张表的确定性明细行。

### ⚠️ 负面 / 技术债

1. **`db-export` 的矩阵是显式枚举的**（5 表 × 4 格式），不像路径端点那样自动发现。
   枚举的是端点自带的封闭列表（跟端点自己校验的那两份一致），所以新增一个 table
   必须同时改端点和这里 —— 漏了会显式地不一致，而不是悄悄漏掉
2. **fixture 铺明细行会让 ADR-0012 的响应体快照基线整体漂移**（数组从空变成有元素），
   所以明细行**默认不开**，只有本门禁自己开 —— 这是刻意的隔离
3. **`export_cycles_csv` 的 `columns` 列表仍然是手写的**。本 ADR 补齐了它，
   而且门禁会守住它，但根子上「SELECT 的列」和「CSV 的列」还是两处 ——
   彻底消除需要把 CSV 导出改成从行字典推列（那会改变空表时的表头行为），留待后续
4. **db-export 的 `since_sim_day` 过滤在 CSV 往返下曾依赖字符串比较**，现在
   `sim_day` 是整数了。过滤逻辑已同时兼容两种形态，但这是行为变更，
   已写进 commit 说明

## 备选方案

- **只冻基线，不做跨格式一致性** —— ❌ 否掉：基线本身漂移的话门禁会一直绿，
  **绿得没有意义**。第二层不需要任何基线，它永远是真的
- **把 CSV/Parquet 也塞进 ADR-0012 的响应体形状快照** —— ❌ 否掉：ADR-0012 抽的是
  JSON 结构，CSV 是**有序的文本表**、Parquet 是**带类型的 schema**，判据完全不同。
  硬塞进去会让那个门禁同时承担两种语义，破坏它已有的清晰度
- **手写导出端点清单** —— ❌ 否掉：这就是 ADR-0013 推翻的 fail-open 设计。
  新加一个导出端点 → 自动进契约 → 没冻进基线 → 红灯
- **列顺序变化一律当兼容** —— ❌ 否掉：位置型读取器（`awk -F, '{print $3}'`）
  会**静默读到别的列**，正是「静默算错比报错更贵」那条原则要防的
- **列顺序变化一律当破坏**（连末尾追加也红） —— ❌ 否掉：末尾追加不影响任何已有
  列的位置，是**真的兼容**。门禁一旦「什么变化都报红」，团队就会开始无脑刷基线

## 面试怎么讲（30 秒）

> 我的项目有四层 API 契约门禁，但第四层自己写下了一张欠条：它把 14 个导出端点
> 豁免了，备注写「字段契约是列名」—— 可列名从来没有被冻过。于是我补了第五层：
> 真起服务真调端点，把 CSV/Parquet/NDJSON 的列名、顺序、类型冻进 CI。
> 关键是我没只冻基线 —— 我加了一条**不需要基线的结构不变量**：同一张表在不同格式下
> 列集合必须一样。这一条当场抓出三个真 bug：CSV 少一列 `n_routes`；统一导出接口
> 把所有数字变成字符串，客户 `sum()` 得到 `'10.012.5'` 而不是 `22.5`，**静默算错**；
> 还有个导出返回的是 placeholder 假 CSV。
> 这就是「门禁本身也要被审计」—— 前一层留下的洞，是下一层的入口。

## 怎么在面试里用

这是 ADR-0011 / 0012 / 0013 的**第四条**「门禁有闭环」故事线。
建议不要四条全讲，挑 ADR-0013 + ADR-0014 一起讲（它们是**同一条线的前后两段**）：

> 「我做到第四层契约门禁的时候，发现第四层自己留了个洞 —— 它把导出端点豁免了，
> 备注写着『字段契约是列名』，但列名其实没人管。我把它补上以后，最有价值的不是
> 又冻了一份基线，而是我加了一条**不需要基线的结构不变量**：同一张表在不同导出
> 格式下必须长得一样。它当场抓出三个 bug，其中一个是我最想讲的：统一导出接口
> 内部绕了一圈 CSV，导致所有数字列都变成字符串，客户在 pandas 里 sum 一下
> 得到的是 `'10.012.5'` —— **不报错，算错了**。
> 这条正好对应 JD 里的『生产级 AI 系统』和『把痛点转化为产品需求』：
> 客户不会告诉你『你的 Parquet 类型不对』，他会告诉你『我们的月度报表数字看着不对』。」

追问预案：

- **「为什么不用现成的 schema 工具（OpenAPI / JSON Schema）？」**
  → OpenAPI 只描述 JSON 响应体；导出文件不是 JSON。而且 CSV 的契约是**有序**
  的（位置型读取器依赖顺序），JSON Schema 表达不了顺序语义。
- **「为什么不用 dbt / Great Expectations 那套？」**
  → 那些管的是**数据内容**（值域、空值率、分布），我管的是**结构契约**
  （有哪些列、什么顺序、什么类型）。结构漂了，内容校验根本跑不起来 ——
  少一列的时候，值域校验全绿，但客户的报表少了一列。
- **「Parquet 类型变了为什么算破坏？」**
  → 因为 Parquet 的 schema 是**自描述**的，客户端 `pd.read_parquet()` 之后
  `df['x'].sum()` 的行为完全由列类型决定。类型从 double 变 string，
  客户的算术**静默失效** —— 这跟 ADR-0012 里「类型被加宽」判红是同一条原则。
- **「跨格式一致性会不会误报？」**
  → 不会，因为它只比较**同一张逻辑表**的不同格式。表名是从导出路径 / db-export
  的 `table` 参数推出来的，`perturbed-supplies`（只有 CSV）这种单格式的表直接跳过。
