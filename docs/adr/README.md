# Architecture Decision Records (ADR)

这个目录记录 **green-logistics-ai 的架构决策**：每个「为什么这么做」背后的背景、备选方案、
代价和被推翻的选项。

**为什么 FDE 岗需要它？**
FDE 的工作现场反复被问的一句话就是「为什么这么设计，而不是另一种？」。
代码只能回答「做了什么」，ADR 才能回答「凭什么」—— 这是从「写代码的人」到「能被客户追问的人」
之间最缺的一块。

> 纪律：ADR 写完不删。被新决策推翻时，新增一条 ADR 并把旧的标成 `Superseded by ADR-XXXX`。

## 怎么在面试里用

不要 7 条都讲。挑 **2-3 条**，每条按同一个四段式讲，2 分钟以内：

```
背景（当时要解决什么） → 备选（考虑过什么，为什么否掉） → 决策（选了什么） → 代价（代价是什么，怎么缓解）
```

推荐组合：

- **0001 多智能体编排** → 讲「为什么不 LangGraph」，这是 multi-agent 岗最常问的一刀
- **0004 韧性 + 可观测** → 讲「客户现场 429 怎么办、成本怎么回答」，对应岗位要求里的
  tokens/sec、cost-per-request
- **0006 CI 策略** → 讲「我交付的东西自己先得是绿的」，这是 FDE 区别于纯后端的地方
- **0008 SDK 迁移** → 讲「我自己写的债我自己还，而且迁移时还挖出了一个真 bug」，
  这是「生产级 AI 系统」最直接的证据
- **0009 持久化层拆分** → 讲「9,949 行单文件 → 16 个模块，公开 API 一个字没改，
  1,600+ 测试全绿」，这是「交付到客户现场还要能长期维护」的证据
- **0010 公开 API 契约测试** → 讲「**而且以后一直会是这样**」：
  我没有靠人盯，我写了个 CI 门禁，每次 push 都校验 104 个方法的签名，
  改一个默认值就红。这是「工程判断有闭环」的证据
- **0011 HTTP API 契约测试** → 讲「**分层门禁 + 单一事实来源**」：
  破坏性变更红、兼容性变更只打印（否则大家会无脑刷基线，门禁就废了）；
  而且它第一天就抓到「对外公布哪些端点要 token」的清单漂了 4 个端点 ——
  我的修法不是补清单，而是改成**从路由表推导**，结构上不可能再漂。
  这是「客户现场的安全面也要有闭环」的证据
- **0012 响应体运行时形状快照** → 讲「**方向感**」：
  我知道 OpenAPI 对 `Dict[str, Any]` 的响应体是瞎的，所以补了第三层契约 ——
  真起服务、真实调端点，把响应压成结构形状冻进 CI。
  字段被删 / 类型被加宽（原来保证是 number，现在可能是 null）→ 红；
  新增字段 / 类型被收窄 → 只打印。因为**加宽**会把客户的代码打炸，**收窄**只是安全方向。
  我当场验证过门禁真的会响：注入「把 number 改成可能为 null」，CI 精准变红。
- **0013 端点自动发现 + 显式豁免登记册** → 讲「**发现自己的门禁有盲区**」：
  上一版契约只覆盖 45/119 个 GET 端点（38%），而且失效得很安静 ——
  有人新加端点，门禁压根看不见。我改成从路由表自动发现 + 显式豁免登记册，
  覆盖率提到 84%，新端点自动进覆盖范围。
  关键设计是**豁免理由做成封闭枚举**（不是「我觉得不重要」），
  以及**端点被豁免要判红**（客户少了一层保护 = 破坏）。
  我还量过一件事：OR-Tools Pareto 从 50 秒限到 2 秒，响应体形状 md5 完全不变 ——
  说明我们冻的是结构，不是性能。这是「**门禁本身也要被审计**」的证据
- **0014 导出端点的列契约冻结** → 讲「**上一层的欠条，下一层来还**」：
  0013 把 14 个导出端点豁免了，备注写着「字段契约是**列名**」——
  可列名从来没被冻过（前面四层都盖不住：签名/HTTP面/JSON 形状/端点发现，
  没有一层在看「导出的 CSV 里到底有哪些列」）。
  我补上第五层，而且**没只冻基线** —— 我加了一条**不需要基线的结构不变量**：
  同一张表在不同导出格式下，列集合必须一样。
  这一条当场抓出三个真 bug：CSV 少一列 `n_routes`；统一导出接口绕了一圈 CSV，
  把所有数字变成字符串，客户 `sum()` 得到 `'10.012.5'` 而不是 `22.5`（**静默算错**）；
  还有一个导出返回的是 placeholder 假 CSV。
  这是「**门禁本身也要被审计**」这条线的**最强证据** ——
  你的门禁可能正在放过你自己没意识到的东西

- **0015 API 层拆包** → 讲「**先把刀磨快，再下刀**」：
  前面五轮契约都在回答「怎么证明没改坏」，这一轮才终于能回答「怎么改得动」——
  `main.py` 8,303 行 / 136 个端点 / 6 个领域挤在一个文件里，
  改一行要读 8,000 行，agent 面对它只会绕开。
  我把它拆成「薄壳 + router 包」（第一个包：82 个 persistence 端点，main.py -43%），
  **公开 HTTP API 一个字节没变** —— 而且这个「没变」不是我说，是四层门禁证出来的。
  迁移用 AST 而不是正则（正则会被 docstring 里的字符串骗），且沿函数引用做**传递闭包**
  （端点用到的私有 helper 一起搬）。
  最值得讲的一个取舍：`coordinator` 我**没有**放 `app.state`，
  因为既有测试直接写 `backend_main.coordinator = fake`（模块属性）——
  为了不改测试、不破坏既有约定，router 每次请求惰性读一次模块属性，
  零同步代码、零测试改动。
  这是「**重构不能以改测试为代价**」的证据

- **0016 复杂度棘轮门禁** → 讲「**让门禁真的有牙齿**」：
  我们的 `max-complexity=10` 写在那里，CI 里跑着 `--exit-zero` ——
  **从来没红过**，复杂度 36 的函数就那么躺在主干上。
  我没有一刀切改严（49 个函数一次爆红 = 巨型重构 + 规则立刻被无视），
  而是做成**棘轮**：已有函数不许变难 / 新函数必须 ≤ 10 / 基线里的函数消失 → 红
  （沉默的缺口必须是红的）。度量：486 个函数里超阈值的 54 → 49，
  persistence router 模块**全部**降到阈值内，而公开 HTTP API **一个字节没变**。
  门禁上线**当天**抓到两个真 bug：
  ① **测试的顺序依赖** —— startup 会重建 coordinator，测试把 pref 写进了一个
  **没人会读的 DB**；全量跑恰好是对的，单跑就红 —— **CI 的绿灯是运气，不是证据**；
  ② `set` 的迭代顺序 —— 同一个请求在两个进程里可能**自动选了不同的 method**，
  没有报错、没有告警、CI 全绿。
  这是「**技术债要有棘轮，而且门禁要能抓到真 bug**」的证据

四条合起来正好覆盖 JD 里的「解决方案架构」「技术决策权衡」「把痛点转化为产品需求」。

## 模板（新增 ADR 时复制这个）

```markdown
# ADR-XXXX: <标题>

- **状态**：提议 / 已接受 / 已弃用 / 被 ADR-YYYY 取代
- **记录日期**：YYYY-MM-DD
- **相关代码**：path/to/file.py, path/to/other.py

## 背景
当时要解决什么问题、有什么约束。

## 决策
我们决定怎么做（写成祈使句，一句话能概括）。

## 备选方案
考虑过哪些做法，为什么没选（每条写「否掉的原因」）。

## 后果
**正面**：…
**负面 / 技术债**：…
```
