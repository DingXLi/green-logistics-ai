# ADR-0020: 门禁视野普查 —— 把「覆盖面 = 价值上限」从一道门禁推广到全仓库

- **状态**: 已接受 (2026-11-15)
- **取代/延续**: ADR-0019 (断言方言覆盖门禁) —— 本 ADR 是它的**推广**
- **相关**: ADR-0016 (复杂度棘轮) · ADR-0017 (测试顺序无关性) · ADR-0018 (松断言门禁) · ADR-0019 (断言方言覆盖门禁)

---

## 一、背景: ADR-0019 只修了一道门禁的视野

ADR-0019 那天抓到的教训被写进了 ADR-0019 的结尾:

> **「我消灭了一整类」这句话, 要用「分母」来证明, 不能用「感觉」。**
> 门禁的覆盖面是门禁的属性, 不是门禁作者的属性。

那天做了一件事: 给**松断言门禁**加「视野自证」—— 门禁普查仓库里出现的
每一种断言方言, 出现一种它不认识的 → 红。ADR-0019 的验收线是:
`tests/` 里一条松断言都不许剩 + 视野必须 100%。

**但那天只做了一道门禁的视野。**

仓库里现在有 3 类 20 多道门禁(契约冻结 / 顺序无关性 / 复杂度棘轮 / 松断言 /
端点策略 / 载荷形状 / 导出列 / 清单自动发现 …)。它们的视野各是多少?
**没人算过。**

而更危险的是: 「视野不足」这件事**不会让任何东西变红**。
一道只看得见 67% 代码的门禁, 照样每天报「✅ 通过」。

---

## 二、决策

### 决策 1: 门禁的视野必须被**算**出来, 不能靠注释承诺

新增 `scripts/gate_vision_census.py`(**门禁视野普查**), 对每道门禁做三件事:

1. **算它的关注面(universe)** —— 「这类问题应该存在在哪」的全集。
   - `PRODUCTION_PY`: 所有非测试 Python 文件
   - `ALL_PY`: 所有 Python 文件
   - `PY_WITH_ASSERTS`: 所有**代码上**含断言的 Python 文件(用 AST 判定,
     免得把 docstring 里的 `assert` 字样算进去)

2. **读它自己声明的扫描范围(scope)** —— **从门禁自己的源码里读**, 用 AST
   把 `SCAN_PATHS` / `DEFAULT_SCAN_PATHS` 这种模块级常量解析出来;
   CI 里的门禁则从 workflow YAML 的 run 段里把路径 token 抠出来。

3. **算覆盖率, 和门禁自报的门槛比** —— 低于门槛 → 红。

> **为什么必须读源码而不是抄登记册**: 抄登记册 = 登记册和代码可以各说各话,
> 而「登记册说自己管 A, 代码实际扫 B」正是 ADR-0017 那类漂移的翻版。
> 从源码里读 → 登记册和代码不一致时, **门禁自己会红**。

### 决策 2: 「A 和 B 完全一致」这类注释里的承诺, 要能被验证

iter #84 的复杂度棘轮门禁, 源码注释里写着:

> 「扫描范围: 与 CI lint job 的 flake8 目标完全一致
> (少扫一个目录 = 那个目录的复杂度债根本不在门禁视野里)」

**这句话从来没被验证过。** 两处各自写一遍目录名, 哪天只改一边, 注释就成了谎言 ——
而谎言不会让 CI 变红。

普查新增 **mirror 段**: 两道门禁被登记为镜像 → 范围必须**逐项相等**,
不等 → 红。

### 决策 3: 有意收窄的视野, 登记在案 + 持续测量, 而不是写死

有些门禁的视野天生就是有意收窄的(比如 `mypy` 只管有类型标注的代码)。

- 把它藏起来 = 又一次「我只看得见我看得见的那部分」;
- 把它写成红灯 = 门禁变成永远红的噪音机, 大家就会去改门槛。

第三条路: **`known_gaps` 段** —— 登记在案, **持续测量**, **不阻断 CI**。
缺口不会变大, 也不会被忘掉; 等条件成熟再升格为正式门禁。

## 三、实测结果: 门禁上线当天就抓到 1 个真盲区

普查上线时仓库的现状:

| 门禁 | 关注面 | 实际扫描 | 视野 |
|---|---|---|---:|
| 复杂度棘轮 | PRODUCTION_PY (62 个文件) | agents, optimization, synthetic, data, web/backend | **42/62 = 67.74%** ❌ |
| CI flake8 lint | PRODUCTION_PY (62 个文件) | 同上 | **42/62 = 67.74%** ❌ |
| 松断言 | PY_WITH_ASSERTS (123 个文件) | tests, selftest | 123/123 = 100% ✅ |

也就是说:

> **「新函数必须 ≤ 10」这句话, 对 27.9% 的生产代码根本不成立。**
> 而这件事没有任何东西会发现。

### 盲区里藏着什么

被遮住的是 `scripts/`(18 个文件, 6,070 行)和根目录的 `debug_script.py`:

- `scripts/loose_assert_lint.py` —— ADR-0018 的松断言门禁本体(800 行)
- `scripts/gen_export_contracts.py` —— ADR-0012 的导出列契约生成器(700 行)
- `scripts/test_order_gate.py` —— ADR-0017 的顺序无关性门禁
- `scripts/gate_vision_census.py` —— 本门禁自己

**换句话说: ADR-0016 ~ ADR-0019 这四道门禁的「实现代码」本身,
一道都没被复杂度棘轮管过。** 这是最讽刺的部分, 也是最值得写下来的部分。

### 一个反直觉的发现: 最该被管的目录反而是最干净的目录

| 目录 | 函数数 | 超阈值(>10) | 占比 |
|---|---:|---:|---:|
| 原来在视野里的 5 个目录 | 503 | 49 | 9.7% |
| 一直不在视野里的 `scripts/` | 195 | **2** | **1.0%** |

看不见的那 27.9%, 质量比看得见的 72.1% 更好。

> **盲区不只是在藏债 —— 也在藏证据。**
> `scripts/` 里 195 个函数只有 2 个超阈值, 说明这个代码库**有能力**
> 在阈值 10 以内写代码(那两个例外是 `test_order_gate.py` 的两个老函数)。
> 「我们做不到」这个假设, 有时候只是「我们没量过」。

## 四、修法

### 修法 1: 两边一起扩(棘轮 + CI lint)

- `scripts/gen_complexity_baseline.py`: `SCAN_PATHS` 从 5 个目录扩到
  `["agents", "optimization", "synthetic", "data", "web/backend", "scripts", "debug_script.py"]`
- `.github/workflows/ci-cd.yml`: flake8 目标同步扩到同一组路径
  —— **两边一起扩**, 镜像声明才继续成立

扩完之后: 棘轮从 503 个函数变成 **691 个**, 超阈值函数**仍然是 49 个**
(净新增 0 笔债 —— `scripts/` 是**带着 0 笔新债**进入棘轮的)。

### 修法 2: 新进入视野的目录, 不带着债进来

`scripts/test_order_gate.py` 的两个超阈值函数(复杂度 15 / 12)不豁免, **当场重构**:

- `scan_ambient_writers` (15) → 拆出 `_singleton_write_lines` + `_root_name`
- `main` (12) → 拆出 `_run_seeds` + `_print_unstable`

行为等价性用**同一份旧代码对照**验证过:
`scan_ambient_writers` 的输出**逐字节相同**(25 个文件 / 79 处命中),
`build_cohort` 两种模式输出也相同。

> **注意这里的取舍**: 「新债不许进场」这条规则意味着, 扩视野的那一刻
> 门禁会立刻红。如果选择 `--write` 豁免, 那是把新债记进账本;
> 我们选了重构 —— 因为**一个刚进入视野的目录应该带着 0 笔债进场**,
> 否则「扩视野」就变成了「扩债务」。

### 修法 3: 普查脚本自己不许有超阈值函数

新写的 `gate_vision_census.py` 一开始有 4 个超阈值函数
(`_workflow_step_paths` 21 / `validate_registry` 13 / `print_report` 13 /
`_module_constants` 11)。**是扩范围后第一次跑棘轮把它自己抓出来的** ——
它当时还不认识自己, 是 `scripts/` 进入扫描范围之后才被看见的。

当场重构到全部 ≤ 10。理由很硬:

> 它是「所有门禁的门禁」。如果它自己写得很复杂,
> 那它对别人的复杂度要求就只是空话。

自测里有一条专门盯着这件事(`test_census_script_itself_is_under_complexity_threshold`)。

### 修法 4: 自测必须进 CI

新增 `selftest/test_gate_vision_selftest.py`(15 条), 造一个**假仓库**在
tmp_path 上验证:

- **有牙齿**: 把扫描范围收窄到只管一半 → 必须判红
- **不误伤**: 范围覆盖全集 → 必须绿
- **不空转**: 视野百分比是**算出来的**, 登记册把门槛写成 10% 也骗不了它
- **fail-closed**: 关注面未知 / 实现文件不存在 / 常量读不到 / 关注面算空 /
  重复 id / 非法门槛 / 悬空镜像引用 / 镜像缺 why → 全部判红
- **镜像校验**: 两道门禁声明一致但范围不同 → 判红

**「一个只报绿的门禁没有价值」** —— 这条规矩从 ADR-0018 用到今天,
现在覆盖仓库里所有门禁。

## 五、后果

### 正面

- 复杂度棘轮门禁的视野从 **67.74% → 100%**(42/62 → 62/62 个生产文件)
- CI flake8 lint 的视野同步 **67.74% → 100%**
- 「与 CI lint job 完全一致」从**注释里的承诺**变成**CI 里可验证的不变量**
- 以后新增一个顶层目录 → 普查立刻报「这个目录没有任何门禁在看」
- 门禁作者再也不能只靠注释说「我管住了」—— 数字会说话

### 负面 / 技术债

- `mypy` 的视野只有 58.06%(36/62), 已登记在 `known_gaps`,
  **不阻断 CI**, 但每次普查都会把数字打出来
- 普查本身是一个**元门禁**: 它自己不阻止任何 bug, 只阻止「门禁的自欺」
- 关注面的定义(`PRODUCTION_PY` / `PY_WITH_ASSERTS`)是人定的,
  定错了普查就失去意义 → 所以「关注面算出来是空的」被判红

## 六、教训(写给未来的自己)

1. **修一道门禁的盲区, 和知道「有几道门禁有盲区」, 是两件事。**
   ADR-0019 把松断言门禁的视野做到 100%, 感觉上「视野这件事解决了」。
   实际上仓库里有 6 类门禁, 只有 1 类被量过。
   **教训: 修了 N 道门禁的视野之后, 下一个任务是「把这件事推广到剩下的」** ——
   而且要**用工具**推广(普查脚本), 不要靠人肉挨个检查。

2. **「我以为我管住了」和「我确实管住了」之间, 差一个分母。**
   复杂度棘轮一直写着「新函数必须 ≤ 10」, 听起来是全仓库的承诺 ——
   实际上它只覆盖 67.74%。**承诺的分母必须是全部。**

3. **盲区里藏的不只是债, 还有证据。**
   `scripts/` 的复杂度超阈值率是 1.0%, 可见部分是 9.7%。
   看不见的那部分, 恰恰是**证明「我们做得到」的证据**。
   只盯着看得见的地方, 会误判自己的能力边界。

4. **元门禁是便宜的, 而且比任何单点修复都更耐用。**
   普查脚本 700 行, 一次投入, 以后每个门禁改动都被它盯着。
   而单点修复(把 `scripts/` 加进 `SCAN_PATHS`) 明天就可能被人改回去 ——
   **除非有什么东西在盯着它。**

5. **「范围收窄」和「范围扩张」都是有代价的决策, 要写进账本。**
   扩视野让棘轮当天就红(2 笔新债)。选择重构而不是豁免, 是因为
   **「进入视野的目录应该带着 0 笔债」** —— 否则扩视野就变成了扩债务。

- `python scripts/gate_vision_census.py` → 退出码 0
- 三道门禁视野均为 100%
- 镜像声明 `complexity-ratchet ≡ flake8-lint` 成立
- `python -m pytest selftest/test_gate_vision_selftest.py -q` → 全绿
- `python scripts/gen_complexity_baseline.py` → 无阻断项(691 函数 / 49 超阈值)
- `python scripts/loose_assert_lint.py` → 0 违规 / 视野 100%
