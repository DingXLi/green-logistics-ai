# ADR-0012: HTTP 响应体运行时形状快照

- **状态**：已接受
- **记录日期**：2026-11-06
- **相关代码**：scripts/gen_payload_shapes.py, tests/test_payload_shapes.py, tests/http_api_payload_shapes.json, .github/workflows/ci-cd.yml

## 背景

iter #78 (ADR-0010) 冻结了 `agents/persistence` 的**公开方法签名**。
iter #79 (ADR-0011) 冻结了 **HTTP 面**: 路径 / 参数 / 状态码 / response_model / 鉴权依赖。

但 ADR-0011 自己白纸黑字写下了**已知边界**:

> 「136 个端点里绝大多数响应是 `Dict[str, Any]`，OpenAPI 里没有 response_model，
> 所以响应体字段在 schema 层面根本看不见。」

也就是说: 契约冻结了三层, 还差**最后一层** —— 客户真正收到的那坨 JSON 长什么样。

这一层对客户**最要命**, 因为下面这些事故 schema 层全部看不见:

| 事故 | schema 层看得见吗 | 客户侧后果 |
|---|---|---|
| 字段从 `integer` 变成可能为 `null` | ❌ | JS 端 `data.x.toFixed(0)` → TypeError |
| 类型从 float 变成 str(为了塞货币符号) | ❌ | 客户算术全错，**且不报错**(静默算错比报错更贵) |
| 字段整个被删(重构顺手删的) | ❌ | 客户报表那一列静默变成空白 |
| 响应多出字段(泄漏绝对路径 / 内部 id) | ❌ | 信息泄漏 |
| 端点整个挂了(500) | ✅(状态码) | — |

而 FDE 岗位的 JD 里写得很直白: 「从概念到上线」「部署到客户现场」。
在客户现场, 这些事故的表现是**对方的系统开始报错**, 而我们完全不知道是自己改的。

## 决策

**用一份确定性 fixture DB 真起一次服务, 真实调一遍端点, 把响应 JSON 递归压成
「结构形状」快照, 交给 CI 每次比对。**

具体三条:

1. **机械生成, 不手写** —— `scripts/gen_payload_shapes.py` 真起服务、真调端点,
   快照是**观测**出来的, 不是人抄出来的。
2. **只记结构, 不记值** —— 值每天都在变, 结构才是客户依赖的契约。
   形状 = 类型集合(可并集) + 对象字段(递归) + 数组 item 形状(合并)。
3. **确定性** —— 用 `scripts/seed_ci_fixture.py` 铺一份 14 天的合成 cycle,
   世界引导用固定 seed=42, 快照**两次跑字节级一致**。
   (不可复现的门禁 = 随机噪音的门禁 = 会被所有人无视, 真破坏也会被一起无视。)

### 分层断言(和 ADR-0010 / ADR-0011 一脉相承)

| 变化 | 判定 | 理由 |
|---|---|---|
| 端点不在快照里了 | 🔴 红 | 端点被删 / 改名 |
| 状态码变了 | 🔴 红 | 客户走错分支 |
| **字段被删** | 🔴 红 | 客户拿不到这个值了 |
| **类型集合被加宽**(integer → integer\|null) | 🔴 红 | **客户原来的类型假设失效** |
| **类型集合被替换**(integer → string) | 🔴 红 | 静默算错 |
| 新增字段 | 🟡 黄 | 兼容 |
| 新增端点 | 🟡 黄 | 兼容 |
| **类型集合被收窄**(integer\|null → integer) | 🟡 黄 | 对客户是安全方向 |
| `unknown`(空数组无样本) 相关变化 | 🟡 黄 | 数据出现了, 不是破坏 |

理由和 ADR-0011 一模一样: **门禁一旦「什么变化都报红」, 团队就会开始无脑刷基线 ——
那它就废了。** 所以「加宽」红、「收窄」黄, 是这个门禁能活过三个月的关键。

### 「加宽」为什么红、「收窄」为什么黄

这是整个设计的核心判断, 值得单独说:

- **加宽**(原来保证是 number, 现在可能是 null 了) → 客户的 `x * 2` / `x.toFixed(0)` 会炸 → 红。
- **收窄**(原来可能是 null, 现在保证有值了) → 客户原有的 null 分支还在, 只是走不到了 → 黄。

一句话: **门禁的方向感必须朝着「客户会不会炸」, 而不是朝着「diff 有没有变」。**

## 备选方案

1. **给所有端点补 `response_model`(Pydantic)** → 否掉。
   136 个端点全补 response_model 是一个多周的工程, 而且它解决的是「**未来**别再写成
   `Dict[str, Any]`」, 解决不了「**已经**写好的 136 个端点现在返回了什么」。
   → 这件事的正解是**先把现状冻住**(本 ADR), 再逐步收窄。

2. **直接用 OpenAPI 快照比对** → 否掉。
   ADR-0011 已经论证过: 响应体退化到 `Dict[str, Any]` 时 OpenAPI 是瞎的;
   而且 description 一改就红, 噪音大到没人看。

3. **用 JSON Schema 校验每个响应** → 否掉。
   要给每个响应写一份 schema, 等于把 136 个端点的响应**再手写一遍** ——
   手写的东西早晚会和实现不一致, 而门禁的整个价值在于「它是从真实行为里长出来的」。

4. **不冻结, 只靠 code review + 集成测试** → 否掉。
   「集成测试」测的是**这个端点在当前实现下返回什么**; 一旦有人改了实现,
   集成测试会跟着一起变绿 —— 它**测不出破坏**, 只测得出「现在是这样」。
   要测出破坏, 需要一个**不由被测对象生成的期望值**。

5. **只记录顶层字段名, 不记录嵌套和类型** → 否掉。
   那就测不出「类型从 number 变成 string」这类**最贵的**事故(静默算错)。

## 后果

**正面**

- 客户可见的响应体**第一次有了 CI 常驻不变量** —— 三层契约(Python API / HTTP 面 / 响应体)齐全。
- 快照里显式记下了 **35 个「可能是 null」的字段** —— 这正是 OpenAPI 说谎的那一面,
  客户可以据此写防御代码, 我们也可以据此写文档。
- 快照规模: **45 个端点 / 891 个字段 / 122 KB**, 覆盖概览面 + 持久化分析面 + 运维面。

**负面 / 技术债**

- 采集要真起一次服务(约 4 秒), 所以门禁跑在 **子进程**里
  (要独占 `GL_DB_PATH` 和 app 的 import, 不能和别的测试共用同一份 app 单例)。
- 快照里**只记结构不记值** → 值的语义变化(比如单位从吨变成公斤)测不出来。
  → 这是刻意的取舍: 值变了要靠业务测试管, 结构变了才要靠门禁管。
- 端点清单(`ENDPOINTS`)是**手写**的 45 条 → 新端点不会自动进快照。
  → 已用 `test_baseline_covers_expected_endpoints` 守住下限, 但「自动发现全部端点」
  留给后续(难点是筛掉有副作用 / 打外网 / 调 LLM 的端点)。

## 验证(全部实测, 非推断)

### 1. 注入 4 种破坏 → 确认门禁真的会响

| 注入的破坏 | 门禁抓到了吗 | 报出来的信息 |
|---|---|---|
| 删掉 `summary.llm_decisions` 字段 | ✅ 红 | `summary.llm_decisions: 字段被删 —— 客户拿不到这个值了` |
| `total_cost_sek`: number → string | ✅ 红 | `summary.total_cost_sek: 类型被替换 ['number'] → ['string']` |
| `cycle-history` 最后一项 `total_tons` 变 null | ✅ 红 | `cycle-history[].total_tons: 类型被加宽 ['number'] → ['null','number'] (新增 ['null'])` |
| summary 多一个 `cost_per_ton_sek` 字段 | ⬜ 不阻断 | `[兼容变更（仅提示）] summary.cost_per_ton_sek: 新增字段 (兼容)` → exit 0 |

4 次全部符合预期(3 红 1 黄), 随后**完整还原**(`git diff` 为空), 再跑回到 `OK`。

> 第 3 条是本 ADR 的核心价值: **schema 说它是 number, 运行时它可能是 null ——
> 这件事只有真跑一遍才知道**。

### 2. 可复现性

同一份代码连跑两次 `--json`, 输出**字节级一致**(`test_snapshot_is_deterministic`)。
确定性来自: 固定 fixture DB + 固定 seed 的世界引导 + 只记结构不记值。

### 3. 不变量测试

`pytest tests/test_payload_shapes.py` → **15 passed**,
其中 7 条是差异语义的**单测**(「测试测试」):
字段删 = 红 / 字段增 = 黄 / 加宽 = 红 / 替换 = 红 / 收窄 = 黄 / unknown = 黄 /
bool 不能被当成 int。

### 4. 全量 fast 套件

见下方「CI」一节。

## CI 接入

`.github/workflows/ci-cd.yml` 的 `fast-tests` job 增加一步:

```yaml
- name: HTTP payload shape gate (iter #80)
  run: python scripts/gen_payload_shapes.py
```

加在 **pytest 之后、coverage 上传之前**: 「测试挂了」和「形状漂移了」
在 CI 日志里是两条独立的失败原因, 不会互相掩盖。

## 面试怎么讲(30 秒版)

> 「我的后端有 136 个端点, 但绝大多数响应是 `Dict[str, Any]` ——
> OpenAPI 对响应体字段完全是瞎的。所以我补了**第三层**契约:
> 用一份确定性 fixture DB 真起一次服务, 真实调一遍端点,
> 把响应压成**结构形状**快照(只记结构不记值), 冻进 CI。
>
> 关键是**方向感**: 字段被删、类型被加宽(原来保证是 number, 现在可能是 null)
> —— 让 CI 红; 新增字段、类型被收窄 —— 只打印。
> 因为**加宽**会把客户的 `x.toFixed(0)` 打炸, **收窄**只是让老分支走不到。
>
> 我当场验证过门禁真的会响: 注入「把一个 number 改成可能为 null」,
> 门禁精准报出「类型被加宽」并让 CI 变红 —— 这件事 OpenAPI 永远测不出来。」

追问预案:

- **「为什么不干脆给所有端点补 response_model?」** → 那要一两个 sprint,
  而且它解决的是「未来别再写成 Dict[str, Any]」, 解决不了「**已经**写好的 136 个端点
  现在返回了什么」。先把现状冻住, 再逐步收窄 —— 顺序不能反。
- **「为什么不手写 JSON Schema 校验?」** → 手写的期望值早晚会和实现不一致,
  而这个门禁的全部价值在于「它是从真实行为里长出来的」。
- **「空数组怎么办?」** → item 形状记成 `unknown`, 与 unknown 相关的变化一律只提示 ——
  「这个端点以前一直返回空, 现在开始有数据了」是提示, 不是破坏。
- **「值变了测不出来吗?」** → 对, 刻意的取舍: 值变了(比如单位从吨变成公斤)靠业务测试管,
  门禁只管结构。门禁管得越宽, 越会被无视。
- **「这跟 FDE 有什么关系?」** → 客户现场最贵的不是「接口 404」, 是「**对方系统开始静默算错**」。
  我把这三类事故在 CI 里变成红灯, 就是把「客户投诉」提前到了「合并前」。
