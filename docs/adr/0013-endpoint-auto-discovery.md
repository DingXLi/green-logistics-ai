# ADR-0013: 端点自动发现 + 显式豁免登记册

- **状态**：已接受
- **记录日期**：2026-11-07
- **相关代码**：scripts/endpoint_policy.py, scripts/gen_payload_shapes.py, tests/test_endpoint_policy.py, tests/http_api_payload_shapes.json, .github/workflows/ci-cd.yml

## 背景

iter #80 (ADR-0012) 把「响应体在运行时到底长什么样」冻成了 CI 常驻不变量。
那一轮做得很好 —— 三层契约(Python API / HTTP 面 / 响应体)齐全, 方向感清晰
(加宽红 / 收窄黄), 而且四条注入破坏全部实测通过。

但 ADR-0012 自己白纸黑字写下了**已知边界**:

> 「端点清单(`ENDPOINTS`)是**手写**的 45 条 → 新端点不会自动进快照。
>   → 已用 `test_baseline_covers_expected_endpoints` 守住下限,
>     但「自动发现全部端点」留给后续(难点是筛掉有副作用 / 打外网 / 调 LLM 的端点)。」

这一轮就是来还这笔债的。

### 手写清单为什么是**fail-open** 的

我数了一下: 这个后端有 **136 个 HTTP 端点**, 其中 **119 个是 GET**。
ADR-0012 的基线只覆盖 **45 个** —— 覆盖率 **38%**。

也就是说: **六成的客户可见 GET 端点, 它们的响应体可以随时被人改掉,
而 CI 门禁连看都不会看一眼。**

更要命的是**它失效的方式是静默的**:

| 场景 | 手写清单时代 | 门禁反应 |
|---|---|---|
| 有人新加了 `@app.get("/api/xxx")` | 新端点不在清单里 | 🟢 照常绿 |
| 有人把某个端点的字段从 int 改成 str | 不在清单里 | 🟢 照常绿 |
| 有人把整个端点删了 | 不在清单里 | 🟢 照常绿 |

「守住下限」(`test_baseline_covers_expected_endpoints`) 只能证明
「**该保的还在保**」, 不能证明「**新增的也在保**」。这是两个完全不同的问题。

而且清单会**漂**: 人是手写的, 端点是代码生成的, 两者必然不同步。
ADR-0012 自己也承认 —— 快照里只有 45 个端点, 而代码里有 119 个。

### 「自动发现全部端点」的难点在哪

ADR-0012 说难点是「筛掉有副作用 / 打外网 / 调 LLM 的端点」。
我先把这三类端点**逐个实测**了一遍, 发现难点比想象的更具体:

1. **必填参数**: `/api/persistence/compare-materials` 要 `material_a/material_b`,
   `/api/admin/db-export` 要 `table` —— 不给就 422。
   (手写清单里 `/api/admin/db-export` 就是这么漏掉的: 它不在清单里,
   所以没人发现它需要参数。)
2. **路径参数**: `/api/persistence/cycle-detail/{cycle_id}` —— 需要一个
   fixture 里真实存在的 cycle_id。
3. **慢**: `/api/optimize/pareto` 默认参数要 **50 秒**(跑真 OSM 路网 + OR-Tools)。
4. **打外网**: `/api/weather`(SMHI)、`/api/signals/external`(Eurostat)。
5. **调 LLM**: `/api/debug/llm` 会真的调 Gemini。
6. **非 JSON**: 14 个 CSV / Parquet / NDJSON 导出端点。
7. **fixture 造不出来**: `/api/persistence/compare-routes` 要 route_id,
   但 fixture 只铺了 `optimization_cycles`, 没有 `routes` 行。

## 决策

**把「手写端点清单」换成「自动发现 + 显式豁免登记册」, 并把门槛从 fail-open 换成 fail-closed。**

具体四条:

### 1. 自动发现 —— 端点集合来自路由表, 不来自手写清单

从 FastAPI 的 `app.routes` 里枚举全部 GET 端点(`APIRoute` 且 methods == {GET})。
只取 `APIRoute` —— Starlette 自带的 `/openapi.json` / `/docs` / `/redoc`
是普通 `Route`, 不是业务端点, 不进契约。

**覆盖率从 45/119 (38%) 提升到 100/119 (84%)。**

### 2. 显式豁免登记册 —— 每个采不到的端点都要登记 + 说清理由

`scripts/endpoint_policy.py` 里的 `EXEMPTIONS`, 每一条必须写:

- `reason` —— **机器可读的封闭枚举**(`EXEMPTION_REASONS`), 不是自由文本
- `note` —— 一句人话, 回答「客户少了哪层保护, 换来了什么」

理由枚举(每一类都是**机器可判定的事实**, 不是主观描述):

| reason | 判定依据 | 本轮命中 |
|---|---|---|
| `NON_JSON_RESPONSE` | 响应体不是 JSON(CSV/Parquet/NDJSON) | 14 |
| `EXTERNAL_NETWORK` | 响应形状取决于能不能连上第三方 API | 2 |
| `LLM_CALL` | 端点会真的调 Gemini | 1 |
| `REQUIRES_INSTANCE` | 需要运行期才存在的实例 id | 1 |
| `FIXTURE_NO_DATA` | fixture 里没有对应行, 采到的形状是一堆 null | 1 |

**豁免从「沉默的缺口」变成「代码评审能看见的一行登记」。**
以前是「没写进清单就等于没保护」, 现在是「不写豁免理由就别想跑过 CI」。

### 3. 参数绑定 —— 一个机制解决四件事

`PARAM_BINDINGS` 里给路由模板绑定 path/query 参数值。它同时解决:

- **必填参数** —— compare-materials / db-export / compare-cycles
- **路径参数** —— cycle-detail / iot-telemetry
- **成本封顶** —— pareto 默认 **50s** → 限参后 **2s**
- **避开外网** —— `use_real_roads=false`, CI 不依赖 OSM 路网

> 成本封顶这一条是**实测**的, 不是猜的: 限参前后快照 md5 **完全相同**
> (`5a8dcc691652` == `5a8dcc691652`)。也就是说 OR-Tools 算得准不准、
> 用真实路网还是 Haversine, **都不改变响应体的字段结构** ——
> 而字段结构才是我们要冻的东西。

### 4. Fail-closed —— 门禁在三个方向上都会响

这是本 ADR 的核心。**自动发现本身还不够**, 因为自动发现只是「把端点找出来」,
还得保证「找出来的东西真的被冻住了」。三个红灯方向:

| 触发条件 | 判定 | 理由 |
|---|---|---|
| **新端点没冻结进基线** | 🔴 红 | 它已经被采到了, 但基线里没有 → 响应体**没有任何契约保护** |
| **端点从「被采集」变成「被豁免」** | 🔴 红 | 客户可见的契约**消失了** —— 跟「字段被删」同级的事故 |
| **陈旧豁免**(登记的路由已不存在) | 🔴 红 | 死配置; 而且会让人误以为那个端点还被保护着 |
| **豁免理由不在封闭枚举里** | 🔴 红 | 「因为我不高兴」不是理由 |
| **豁免缺 note** | 🔴 红 | 评审时看不懂为什么豁免 |
| **端点从豁免变成被采集** | 🟡 黄 | 保护变强了, 好事 |
| **新增豁免** | 🟡 黄 | 但必须是有意的 |
| **豁免理由变了** | 🟡 黄 | 值得让人知道 |

### 「新端点 = 兼容(黄)」这个旧判断, 为什么必须推翻

ADR-0011 / ADR-0012 都把「新增端点」判成黄色(兼容) —— 在**手写清单**时代这是对的:
新端点不在清单里, 门禁看不见它, 那它跟「已冻结的端点」没有任何可比性。

但**自动发现改变了这个前提**:

> 新端点**会被采到**。于是「基线 → 当前」的 diff 每次都报「新增端点(黄)」,
> 门禁**永远绿**。而这个端点已经在生产上被客户调了 ——
> 它的响应体却**没有任何契约**。

所以在自动发现下, 新端点必须**强制冻结**: 红灯 → 跑 `--write` → 写进基线。
这不是「破坏性变更」意义上的红, 而是「**你欠了一份契约**」意义上的红。

**一句话: 黄灯的意思是「改了没关系」, 但新端点的真实语义是「从现在起有东西要保护了」——
它需要一次有意识的动作(冻结基线), 而不是默认通过。**

### 「加宽红 / 收窄黄」的方向感, 在覆盖范围这一层同样成立

ADR-0012 建立了「门禁的方向感必须朝着『客户会不会炸』」这条原则。
本 ADR 把同一条原则用到了**覆盖范围**这一层:

- 端点被**豁免** → 客户少了一层保护 → 🔴 红
- 端点被**纳入**覆盖 → 客户多了一层保护 → 🟡 黄

方向感一致: **保护变少 = 红, 保护变多 = 黄。**

## 备选方案

1. **只把清单写全**(手写 119 条) → 否掉。
   这只是把「手写清单漂移」换成「手写清单更大更容易漂」。119 条手写清单,
   第一个月就会开始漏。而且「哪些端点不能采」的理由还是散落在代码里。

2. **自动发现, 采不到的直接跳过(不登记豁免)** → 否掉。
   这就是 ADR-0012 的老毛病 —— 沉默的缺口。跳过的那部分永远没人知道,
   直到客户投诉。

3. **用 OpenAPI 自动生成** → 否掉。
   ADR-0011 已经论证过: 绝大多数端点响应是 `Dict[str, Any]`,
   OpenAPI 对响应体字段**是瞎的**。自动发现解决的是「端点在不在清单里」,
   不是「响应体长什么样」—— 后者仍然必须真跑一次。

4. **只覆盖「重要的」端点**(按路径前缀挑) → 否掉。
   「重要」是个主观判断, 而且它会**永久固化**: 今天不重要的端点,
   明天可能就成了客户天天调的接口, 而它依然没有契约。
   主观判断应该体现在**显式的豁免登记**里(带理由、能评审), 而不是体现在
   「谁想起来写进清单了」里。

5. **给外部端点也建契约**(用 fallback 形态) → 否掉。
   实测: `/api/weather` 的 fallback 形态里 `current` 是**空对象 `{}`**,
   `/api/signals/external` 的 fallback 形态多出 `all_values.<YYYY-MM>` 共 54 个叶子。
   冻 fallback 形态 = 冻住「外网不通时的样子」, 而生产环境外网通常是通的 ——
   那时候字段集跟基线不一样, 门禁随机红。
   → 所以外部端点诚实地豁免, 并在 note 里写清两种形态的差异。

## 后果

**正面**

- **覆盖率 38% → 84%**(45/119 → 100/119), 且**新端点自动进入覆盖范围**。
- **门禁从 fail-open 变成 fail-closed**: 三个新红灯方向(未冻结 / 被豁免 / 陈旧豁免)
  都是「以前会静默通过」的场景。
- **豁免有了台账**: 19 个豁免, 5 类理由, 每一类都写清了代价。
- **CI 时长没变**: 限参让 pareto 从 50s → 2s, 整个采集仍然 < 15s。
- **评审有抓手**: 改一行 `EXEMPTIONS` 就是在声明「这个端点不保护了」——
  这行 diff 会被 code review 看见, 而以前它根本不存在。

**负面 / 技术债**

- **多了一份要维护的登记册**: `EXEMPTIONS` / `PARAM_BINDINGS` 是手工维护的,
  端点改名时要同步改。好处是**改漏了会红**(陈旧豁免检查), 不会静默。
- **非 JSON 端点的响应体仍然没有契约**(14 个 CSV/Parquet/NDJSON)。
  CSV 的契约其实是「列名」而不是「JSON 字段形状」, 那是另一个形状的契约, 留待后续。
- **外部端点(2 个)仍然没有契约** —— 它们的响应形状**本质上**依赖第三方可用性,
  冻任何一边都是撒谎。这不是工具的缺陷, 是被冻对象的性质。
- **fixture 只有 `optimization_cycles` 一张表有数据**, 所以
  `compare-routes` 采到的形状是一堆 null(看着像契约, 其实是假的)→ 已豁免,
  并在 note 里写明。

## CI 接入

`.github/workflows/ci-cd.yml` 的 `fast-tests` job 增加一步:

```yaml
- name: Endpoint policy gate (iter #81)
  run: python scripts/endpoint_policy.py
```

加在 **HTTP payload shape gate 之前**: 策略校验是快的(~3s, 不采集),
先跑它 —— 如果登记册里有陈旧豁免或漏登记的端点, 3 秒就报错,
不用等 15 秒的形状采集跑完。

## 面试怎么讲(30 秒版)

> 「我的后端有 136 个端点, 但上一版响应体契约只覆盖了 45 个 —— **38%**。
> 更糟的是它失效得很安静: 有人新加一个端点, 门禁压根看不见, 照常绿。
>
> 我把它换成了**从路由表自动发现** + **显式豁免登记册**:
> 覆盖率从 38% 提到 84%, 而且新端点自动进覆盖范围。
> 采不到的必须登记**机器可读的豁免理由** —— 19 个豁免, 5 类:
> 非 JSON 下载流、外部网络依赖、真调 LLM、要运行期实例、fixture 没数据。
>
> 关键是**方向感**: 端点从「被采集」变成「被豁免」我判**红** ——
> 客户可见的契约消失了, 跟「字段被删」是同一等级的事故。
> 而新增端点我也判红 —— 不是因为它破坏了谁, 是因为**你欠了一份契约**:
> 自动发现已经采到它了, 基线里却没有, 那它的响应体此刻没有任何保护。
>
> 我实测注入过 5 种破坏, 每一种门禁都精准报红。
> 而且我量过一件事: 把 OR-Tools 的 Pareto 求解从 50 秒限到 2 秒,
> 响应体的形状 md5 **完全不变** —— 所以我们能冻住结构, 又不用让 CI 跑一分钟。」

追问预案:

- **「自动发现会不会把不该调的端点也调一遍?」** → 会, 所以有豁免登记册。
  但我把豁免理由做成了**封闭枚举 + 机器可判定的事实**:
  「响应体不是 JSON」「形状依赖第三方 API 可用性」「会真的调 LLM」——
  不是「我觉得这个端点不太重要」。后者会固化, 前者能被评审也能被检查。
- **「外部端点为什么不也冻上?」** → 实测它们的 fallback 形态和 live 形态**字段集不同**
  (weather 的 `current` 在 fallback 下是空对象)。CI 里 `cache/` 被 gitignore,
  所以 CI 永远走 fallback, 生产环境通常走 live —— 冻哪一边都是撒谎。
  诚实地豁免 + 在 note 里写清差异, 比造一个随机红的门禁强。
- **「为什么不干脆给所有端点补 response_model?」** → 那要一两个 sprint,
  而且它解决的是「未来别再写成 Dict[str, Any]」, 解决不了「已经写好的端点现在返回了什么」。
  先冻现状, 再逐步收窄 —— 顺序不能反。
- **「跟 FDE 有什么关系?」** → FDE 的价值就是**在客户现场之前发现问题**。
  客户现场最贵的不是「接口 404」, 是「**对方系统开始静默算错**」。
  这一轮把「六成端点不受保护」这个静默缺口补上了,
  又把「有人偷偷把端点挪进豁免列表」这个后门堵上了 —— 都是往现场之前挪。
