# ADR-0018: 松断言门禁 —— 让「一条断言只证明一件事」成为 CI 常驻不变量

- **状态**：已接受
- **记录日期**：2026-11-13
- **相关代码**：`scripts/loose_assert_lint.py`, `config/loose_assert_exemptions.json`, `selftest/test_loose_assert_selftest.py`, `tests/fake_world.py`, `.github/workflows/ci-cd.yml`
- **相关 ADR**：ADR-0017（测试顺序无关性门禁，本 ADR 是它的同源延续）、ADR-0016（复杂度棘轮门禁）

---

## 背景

ADR-0017 的顺序无关性门禁上线**当天**就抓到了一个真 bug。
它抓到的方式很典型：三个 seed 里有两个红，报告指出「这条测试换顺序就翻转」。
但真正让这条测试翻转的根因，是**三件小事叠在一起**，其中一件是这个：

```python
assert resp.status_code in (200, 503)
```

一个断言**同时接受「成功」和「服务不可用」两种结果**。
翻译成人话：**这条断言什么都没断言**。
端点整个 500 了，测试照样绿；端点返回 503（持久化层没起来），测试也一样绿。

当时的修法是把那一处断言改精确 —— 那是对的，但只修了**一处**。
我们没有问的是：**仓库里还有多少条这样的断言？**

扫描结果：**11 条多值断言**，分布在 4 个测试文件里。
其中最糟糕的一条在 `tests/test_sweet_spot.py`：

```python
assert resp.status_code in (200, 400, 500)
```

三个结果全收 —— 这条测试在「端点根本不能用」的情况下依然是绿的。

更隐蔽的是**条件断言**（后来发现 25 处）：

```python
if resp.status_code == 200:
    assert "cycle_id" in parsed
```

断言写在「看结果再决定要不要断言」的守卫里。
端点一挂 → 整段断言**根本不执行** → 测试通过。
这类断言甚至不会出现在失败报告里 —— 它只是「没说话」。

把两者合起来，是一句话：

> **我们的测试套件里，有一部分测试可以在什么都没证明的情况下通过。**

对一个要交付给客户、要对「这套东西能不能上线」负责的 FDE 来说，
这是最危险的一类债：**它不产生失败，它只产生虚假的安心**。

---

## 决策

**我们把「一条断言只证明一件事」变成一条 CI 常驻不变量。**

具体是：新增 `scripts/loose_assert_lint.py` —— 一个 AST 静态门禁，
扫 `tests/` 下所有测试文件，判定三类失效模式：

### 规则 1：`MULTI_STATUS_IN` —— 同时接受多个状态码

```python
assert resp.status_code in (200, 503)      # ← 违规
assert resp.status_code in (200, 400, 500)  # ← 违规
```

判定：断言是 `<expr> in <container>`，`container` 是 tuple/list/set，
元素里**至少有一个是 100..599 的整数**，且**元素总数 ≥ 2**。

### 规则 2：`MULTI_STATUS_OR` —— 同一表达式的「或」链

```python
assert resp.status_code == 200 or resp.status_code == 503   # ← 违规
```

### 规则 3：`CONDITIONAL_ASSERT` —— 断言写在结果守卫里

```python
if resp.status_code == 200:
    assert "cycle_id" in parsed        # ← 违规: 可能根本不执行
```

判定：断言语句位于某个 `if` 的 body 内，且该 `if` 的条件里出现 `status_code`。
也就是说：**被断言的东西，同时决定了断言跑不跑**。

### 刻意不拦的情况（避免门禁变成噪音机器）

门禁只有精准才有人看。我们明确放过这些：

| 写法 | 为什么放过 |
|---|---|
| `assert resp.status_code == 200` | 精确，拦什么拦 |
| `assert 200 <= resp.status_code < 300` | 区间断言，语义明确 |
| `assert resp.status_code in range(200, 300)` | 区间断言的另一种写法 |
| `assert role in ("admin", "analyst")` | 值域检查，不是「多个可接受结果」 |
| `assert x in (100, 200)` 且 `x` 与 status 无关 | 只看「像状态码的数字」（100..599） |
| `if resp.status_code == 200:` 后面**没有断言** | 只是取数据的冗余守卫，不是失效断言 |

### 豁免登记册 + 四条 fail-closed 不变量

豁免登记册在 `config/loose_assert_exemptions.json`，
key = `path::function::规范化后的断言源码`（**不用行号** —— 行号会漂，
按行号冻结就等于每改一次代码就得刷一次登记册，ADR-0016 的同一条教训）。

理由必须来自**封闭枚举**：
`FLAKY_ENV_DEPENDENT` / `PENDING_REWRITE` / `NON_STATUS_SEMANTICS`。
自由文本的理由等于没有理由 —— 必须能机器判定「这属于哪一类」。

四条不变量（与 ADR-0010 ~ ADR-0017 一脉相承）：

- **不漏**：任何一条松断言，除非显式登记，否则一律红。
- **不腐**：登记册里的豁免如果已经对不上任何现存松断言（改好了 / 删了）→ **红**。
  死豁免会让人误以为「那里还有问题被管着」。
- **不空**：豁免理由必须在封闭枚举里，且必须写清「客户少了哪层保护，换来了什么」。
- **不静默**：一个文件都没扫到 → **红**。ADR-0017 教给我们的：
  「0 个 testcase 收集到 → 判红」，因为**门禁自己瞎了**比「门禁通过」危险得多。

### 同时：把存量还掉

门禁上线当天，**11 条多值断言 + 25 条条件断言全部改精确**，
登记册是**空的**（0 豁免）。

改的方式不是「把 `in (200, 503)` 改成 `== 200`」了事 ——
那需要先让端点行为**确定**：

- `tests/test_llm_cost_forecast.py`：原来的 fixture **什么都不注入**，
  端点能不能跑通全看 ambient coordinator 在不在。
  现在自己造 `Persistence`（临时 DB + 种子数据）+ fake coordinator，
  并**新写一条 `coordinator=None → 精确 503`** 的测试 ——
  旧断言里那半个「503」分支，现在被**真正证明**了。
- `tests/test_carbon_scenarios.py` / `tests/test_sweet_spot.py`：
  抽出共享的 fake 世界 `tests/fake_world.py`（一份语义，两处共用），
  端点行为从此确定。
- `tests/test_persistence_parquet.py` / `test_persistence_json_ndjson.py`：
  先精确断 200，再无条件断内容（原来整段包在 `if ... == 200:` 里）。
- `tests/test_fleet_distance.py`：补上精确的状态码断言，
  顺带把 `use_real_roads=False` 加上（少打一次 OSM）。

**副产品**：因为不再依赖 ambient coordinator 跑真优化，
`tests/test_carbon_scenarios.py` 从 **47 秒 → 2.5 秒**，
而且不再依赖 OSM 可达性 —— 测试第一次变成了**可复现**的。

## 备选方案

**方案 A：只改那 11 条断言，不做门禁。**
否掉的原因：修 bug 是点修复，防 bug 才是整类问题。
下一个人写 `in (200, 503)` 时，没有东西拦他 —— 而这种写法会**自然地**重新长出来，
因为写测试的人那一刻往往还不确定端点会返回什么。
ADR-0017 抓到的那个 bug 就是这么来的。

**方案 B：用 flake8 / pylint 的现成插件。**
否掉的原因：现成规则要么太宽（`in` 一律禁 → 误伤值域检查），
要么太窄（只禁 `in (200, 503)` 这种字面量形式 → 漏掉 `== 200 or == 503`）。
而且它们不认识「HTTP 状态码」这个领域概念。
自己写 300 行 AST 规则，能精确表达「像状态码的数字」和「看结果再决定要不要断言」。

**方案 C：把 `in (200, 503)` 直接判死，不给豁免机制。**
否掉的原因：真实世界里存在**确实**有两种可接受结果的场景
（外部网络抖动、依赖服务降级）。没有豁免机制的门禁，
遇到第一个合理的例外就会被整体关掉 —— 那比没有门禁更糟。

**方案 D：只修多值断言，不管条件断言。**
否掉的原因：条件断言的隐蔽性更高（它不产生失败，它只是「没说话」），
而且**数量是前者的 2 倍多**。只治一半，门禁的说服力会打折。

## 后果

**正面**

- 仓库里**一条**「同时接受多个结果」的断言都不剩，登记册 0 豁免。
- 三条规则 + 四条 fail-closed 不变量，让这类失效模式**不可能悄悄回来**。
- 门禁本身**有自证**：`selftest/test_loose_assert_selftest.py`（23 条）验证
  「有牙齿」（能抓到）+「不误伤」（放过 7 类正常写法）+「fail-closed」（陈旧豁免 /
  枚举外理由 / 重复登记 / 零文件 → 全部判红）。
- 测试套件第一次真正是**可复现**的（不依赖 ambient coordinator，不依赖 OSM）。
- `test_carbon_scenarios.py`：47s → 2.5s。

**负面 / 技术债**

- 门禁目前只认 **100..599 的整数**当状态码。
  将来如果出现「同时接受多个业务枚举值」的同构问题，需要扩规则。
- 规则 3 只看 `if` 的条件里有没有 `status_code`。
  写成 `if resp.status_code in (200, 503):` 的守卫（而不是断言）**不会被**这条规则抓到 ——
  那属于「守卫本身在多值判断」，是下一步可以加的规则 4。
- 门禁只扫 `tests/`。`selftest/` 故意放着「坏代码靶子」，不扫（这是有意的）。
